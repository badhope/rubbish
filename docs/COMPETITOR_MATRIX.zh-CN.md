# 竞品与差异化矩阵

> 目的：锚定 Rubbish「原生特色主题交流论坛」的定位，不照搬通用社区和开源论坛的全部功能。  
> 口径：截至 2026 年 11 月，按公开产品能力与常见自托管部署整理；具体功能以各产品最新版本为准。

## 一、两类竞品

### 通用社区应用

代表形态：Discord、Circle、Facebook Groups、微信群/QQ 群衍生社区。

优势：

- 上手快，发消息门槛低。
- 实时互动强，通知和移动端体验成熟。
- 成员管理、权限、付费社群的商业化路径清晰。

短板：

- 内容按时间流沉底，长文和可检索资料弱。
- 分区与主题纵深有限，讨论容易变成聊天记录。
- 平台锁定强，数据与规则由平台控制。
- 审核多为通用风控或人工，缺少“内容流转 + 运营兜底”的细粒度链路。

### 开源论坛工具

代表：Discourse、Flarum、NodeBB、Vanilla Forums。

优势：

- 分区、标签、版主、举报、封禁等论坛基础设施成熟。
- 可自托管，数据可控，插件生态较完整。
- Discourse 等产品在信任等级、审核队列、SSO、API 方面积累深。

短板：

- 默认面向“大而全”的论坛，配置项多，冷启动需要较多运营人力。
- 审核多依赖版主经验或第三方反垃圾服务；规则可解释性和人工 SLA 不是默认重点。
- 与“长文内容库”的耦合弱，文章与主题帖常是两套系统。
- 移动端与中文场景的细节需要二次开发。

## 三、差异化结论

### 1. 不是“再做一个 Discourse”

Rubbish 的差异不在分区数量、插件数量或版主工具数量，而在内容流转：

- 作品与主题帖共用一个身份、一个通知、一个后台。
- 主题帖先自动初筛，边界内容进入人工队列，处置结果回到作者。
- 规则可解释、可配置、可审计；不依赖大模型黑箱。
- 前台浏览和后台处置之间只隔一个悬浮按钮。

### 2. 不追求通用社区的“大而全”

不做实时语音、短视频流、复杂推荐算法、付费社群。当前阶段把这些能力让给通用平台，把资源集中在：

- 主题帖的可检索、可归档、可追溯。
- 运营人力的可调度、可审计。
- 内容库与论坛的互相引用。

### 3. 开源生态只复用底层

可复用的成熟能力：

- 论坛数据模型、分区树、举报与版主权限。
- 富文本编辑器、草稿、通知、搜索。
- PostgreSQL RLS、Alembic 迁移、对象存储。

不直接引入与核心链路无关的重型插件；所有第三方能力必须接入现有内容流转、权限和审计，否则不进入主线。

## 四、现有短板

| 短板 | 影响 | 计划 |
|---|---|---|
| 无图片/音视频审核 | 违规媒体只能人工发现 | P2 评估视觉审核或人工抽检 |
| 无实时聊天 | 即时互动弱于 Discord | 保持论坛异步，必要时接外部群 |
| 无移动原生 App | 移动端依赖 Web | 先做 PWA/响应式，不急着上架 |
| 无联邦协议 | 无法与其他实例互联 | 暂不做，避免复杂度 |
| 规则语义弱 | 反讽、圈层黑话易漏 | 人工兜底 + 后续小模型可选 |
| 运营数据少 | 难判断规则长期效果 | P1 增加趋势与误判统计 |
| 单机部署 | 高并发上限有限 | 先压测，再按瓶颈拆分 |

## 五、定位一句话

**一个有长文内容库的主题论坛：系统先做可解释的初筛，人来做边界判断，作者能看见自己的内容走到了哪一步。**
