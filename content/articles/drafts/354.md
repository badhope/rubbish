# 前后端一体 Web 托管微服务架构

### ——一个个人级系统的设计、实现与运行观察

---

**摘要**

前后端分离与云原生微服务在过去十年里成为 Web 系统的默认答案，但对于个人或小团队运营的中小规模应用，这套答案的固定成本（构建链、容器编排、服务发现、可观测性中间件）往往超过业务本身。本文描述一个长期运行于单台主机的 Web 系统 Blackbird（内部称 UniServe Framework）：它以"进程托管式微服务"替代容器编排，以自研的长度前缀 RPC 协议替代 gRPC/HTTP 内部调用，并把前端托管、静态资源、流媒体与接口代理合并进一个 C++20 服务，从而在不引入任何前端构建工具的前提下实现同源的前后端一体交付。系统由 11 个常驻进程构成，主链路内存占用约 110 MB，冷启动到全部端口就绪约 17 秒，本机回环下端到端首页响应 12.8 ms。本文给出架构决策的依据、实现中的关键取舍、在一台真实机器上运行一年后积累的运维证据，并诚实地讨论这套架构在什么情况下是错的。

**关键词**：微服务；进程托管；Web 应用网关；前后端一体；RPC 协议；可观测性

## 1 引言

### 1.1 一个被过度设计的问题

我最初的需求很朴素：一个能放笔记、能传文件、能登录、别被脚本小子打穿的网站，跑在自己家里那台机器上。

按 2026 年的标准做法，这件事应该拆成三部分：React/Vite 前端配一条 CI 构建链；Spring Boot 或 FastAPI 后端；外加 Postgres、Redis、Nginx、Prometheus，全部塞进 docker-compose，最好再上个 K8s。我试过。结果是：改一行 CSS 要等构建，跨域问题要配 CORS，内网两个服务互相调用要写服务发现，想看昨天的报错要先学 PromQL。系统的复杂度不再由业务决定，而由脚手架的默认值决定。

这不是说那些工具不好。它们解决的是"几十人协作、每天上百次部署、流量随时翻十倍"的问题。我的场景里这些前提一个都不成立：一个开发者，一台机器，日均 PV 三位数，最坏情况是机器断电。

### 1.2 本文的立场

所以这个系统走向了另一条路，我把它概括成三句话：

1. **编排交给 init 系统**。我不需要 K8s 的调度能力，我需要的是"这 11 个进程挂了要拉起来"。这是 systemd 加一个 200 行的进程托管器的活。
2. **内部通信不需要通用协议**。服务之间只有一种交互形态：发一个 JSON，收一个 JSON。既然如此，一个 4 字节长度前缀加 UTF-8 JSON 的帧协议就够了，而且能在 C++、Python、Go 之间字节级互通。
3. **前端不需要构建**。如果服务端能把页面、样式、脚本、数据和流媒体都从同一个源发出去，浏览器的同源策略就从敌人变成了盟友，CORS、预检、Token 跨域存储这一整类问题直接消失。

这套选择不是"轻量版微服务"，它有自己的内在一致性：**微服务的边界划在数据与信任上，而不划在部署单元上**。

### 1.3 本文的贡献

- 描述一个可运行的、由 11 个异构进程构成的 Web 系统架构（第 3、4 节）；
- 给出自研 RPC 协议与"接口兼容的 C++ 重写"这一演进策略的工程证据（第 5 节）；
- 提出"单一入口 + 三段式信任链"的具体落地方式，并说明每道闸门为何不能合并（第 6 节）；
- 用一次真实的开机链路故障排查，量化说明声明式依赖里"必须"与"最好有"的区别（第 8 节）；
- 给出资源、延迟、启动时间与代码规模的实测数据（第 9 节），并明确讨论适用边界（第 10 节）。

## 2 设计空间与相关取舍

Web 系统的组织形态大致有三档，差别不在技术新旧，而在**固定成本由谁承担**。

**单体（LAMP 式）**：一个进程、一个数据库、一堆静态文件。部署是拷贝，调试是看日志文件。它的上限很低，但只要业务不越界，它几乎没有维护成本。

**前后端分离**：前端成为独立产物（SPA + 构建链），后端只提供 API。收益是前后端可以并行开发和独立部署；代价是引入构建工具、路由、状态管理、跨域配置，以及一门额外的"前端工程学"。

**云原生微服务**：每个服务一个容器，注册发现、配置中心、消息总线、链路追踪全部到位。收益是组织规模的扩展性；代价是**平台本身成为一个需要维护的系统**，而且这个系统通常比业务系统更大。

Blackbird 落在第一档与第三档之间，我称之为"进程托管式微服务"：保留微服务的**能力边界**（鉴权、内容、数据、审核各自独立、独立端口、独立故障域），放弃微服务的**部署形态**（容器、编排、发现）。它与第二档的关系更有意思：它没有回到单体，但把"前端"重新变回服务端的一部分。

表 1 是我对自己这套取舍的坦白账。

**表 1 三种形态的成本对照（个人/小团队视角）**

| 维度 | 单体 | 前后端分离 | 云原生微服务 | 本文系统 |
|---|---|---|---|---|
| 部署单元 | 1 | 2+ | N 容器 | N 进程（systemd 托管） |
| 构建链 | 无 | 必需 | 必需（镜像） | 仅 C++/Go 编译 |
| 跨域问题 | 无 | 有 | 有 | 无（同源） |
| 独立扩容 | 不能 | 部分 | 能 | 不能（单机） |
| 故障隔离 | 差 | 中 | 好 | 好（进程级） |
| 平台维护量 | 极低 | 中 | 高 | 低 |

## 3 架构总览

### 3.1 进程托管：把编排降级为守护

系统的心脏是一个叫 `core`（可执行文件 `nidus.out`）的 C++ 进程。它做三件事：读 `core/services.yaml`、按声明顺序拉起子进程、把子进程的生死报告给 systemd。真正的崩溃重启由 systemd 的 `Restart=` 负责——**我没有自己写重启逻辑，因为写不好**。这一点值得强调：很多自研 supervisor 都死在"重启风暴"和"僵尸进程回收"上，而这两件事 init 系统已经做了二十年。

`services.yaml` 是一份扁平的声明式清单，每条包含 `cmd`、`args`、`depends_on`、`sleep_before`。`depends_on` 目前只用于记录启动顺序，不做拓扑排序——服务数量是 11 个，顺序是人工维护的常量，引入 DAG 求解器属于把问题复杂化。这是刻意的技术债，我在第 10 节会说明它的代价。

`core` 同时内嵌了一个配置分发服务（`:8010`，pymsg 协议），只服务 `gateway.ini` 一个文件。其余服务的配置全部走命令行参数，由 `services.yaml` 注入。为什么只留一个例外？因为 gateway 的路由白名单是需要热更新的——改配置不该重启整个入口。这个"只有一个例外"的设计后来被证明是对的：配置中心是微服务架构里最容易腐化的组件，能砍就砍。

### 3.2 拓扑

除 `waf` 绑定 `*:443` 外，**所有服务都只监听 127.0.0.1**。这不是靠防火墙配置出来的，而是靠 `bind()` 的参数写死的——信任边界是代码里的一行字面量，不是运维脑中的一张图。

### 3.3 一次请求的五跳

一个已登录用户打开首页，请求经过五跳：

1. `waf:443` 终止 TLS，用 coraza 跑 SecLang 规则，命中直接 403；
2. 未命中则转成明文 HTTP 到 `ca:8443`，注入 `X-Forwarded-For` 与 `X-Forwarded-Proto`；
3. `ca` 验签 Token，注入 `X-Auth-User` / `X-Auth-Admin`，转发到 `gateway:8445`；
4. `gateway` 检查白名单（`Proxy.opened`）与身份头存在性，反代到 `fsys:9200`；
5. `fsys` 返回页面；若请求的是笔记接口，再代到 `dnfs2:8006`，后者经 pymsg 落库到 `db2:8005`。

五跳听起来多，但都是本机回环。第 9 节的实测是 12.8 ms——其中 7.6 ms 花在 TLS 握手上，业务本身不到 5 ms。也就是说，**这套分层在这台机器上的代价是可忽略的**，而它换来的是每一跳都能独立限流、独立记日志、独立升级。这个账我认为很划算，但必须承认它依赖"本机回环"这个前提；如果这些服务跨机房，五跳就会变成五次网络往返，结论立刻反转。

### 3.4 端口与信任边界

| 端口 | 服务 | 绑定 | 谁能访问 | 说明 |
|---|---|---|---|---|
| 443 | waf | 0.0.0.0 | 公网 | 唯一入口，终止 TLS |
| 80 | redirect80 | — | 公网 | 当前停用（见 8.3） |
| 8443 | ca | loopback | waf | 认证 + 前置转发 |
| 8445 | gateway | loopback | ca | 纯转发，启动自检强制 loopback |
| 9200 | fsys | loopback | gateway | 前端与流媒体 |
| 8006 | dnfs2 | loopback | gateway/fsys | 树状节点 CRUD |

| 8007 | ai_review | loopback | dnfs2 | LLM + RAG 审核 |
| 8008 | smtp | loopback | ca | 注册验证码邮件 |
| 8009 | captcha2 | loopback | ca | 图形验证码 |
| 8011 | memdb | loopback | — | 内存缓存（暂无调用方） |

## 4 前后端一体的托管模型

### 4.1 "一体"到底指什么

我用这个词指三件具体的事，而不是某种情怀：

**(1) 同源**。页面、样式、脚本、API、图片、视频，全部从 `https://<host>:443` 发出。浏览器的同源策略因此不需要被绕过——没有被绕过的东西，就不会配错。

**(2) 无构建**。前端是手写的 HTML/CSS/JS，存放在 `fsys/public/`，由 C++ 服务直接读文件返回。改一行 CSS 刷新即可见，不需要 Node、不需要 watch、不需要 sourcemap。代价是看不到组件化和 HMR，收益是**部署链上少了一个生态系统**。

**(3) 服务端是唯一的真相源**。`fsys` 不只是静态服务器：它同时是流媒体服务器（HTTP Range，返回 206/416，支持视频拖动）、文件浏览器（realpath 前缀校验防路径穿越）、以及笔记接口的反向代理（解决浏览器不愿直连 `dnfs2` 的问题）。

这里有一个容易被忽略的设计点：`fsys` 代理 `/get_notes` 这类接口，并没有做业务逻辑，只是转发 Authorization 头。**代理与业务严格分离**——这保证了当 `dnfs2` 重写成 C++ 时，`fsys` 一行都不用改（事实如此，见 5.2）。

### 4.2 把"换肤"变成一种数据

树状笔记系统里有一种特殊节点：`style` 与 `theme`。节点内容就是 CSS 或主题变量，作用域限定在节点子树内。也就是说，用户可以给自己的笔记子树换配色，而这件事**不需要任何前端逻辑**——渲染时把节点内容塞进 `<style>` 即可。

我认为这是"前后端一体"最有说服力的副产品：当页面由服务端组装、样式作为数据存储时，个性化就退化成了内容管理问题，而不是前端工程问题。类似的还有 `js` 和 `file` 节点：内容即行为。这套设计当然有安全代价（注入类风险必须靠审核与白名单兜住），但它把"可定制"从代码层搬到了数据层，而数据层是可以审核、可以回滚、可以审计的。

### 4.3 为什么最终没有选 SPA

我认真写过一版 React 前端，后来删了。原因不是性能，而是**状态归属**：这套系统的绝大部分页面是"读多写少的树"，SPA 要在客户端维护一份镜像状态，再与服务器同步，而这份镜像带来的复杂度远大于它省下的那几次页面刷新。树状笔记天然是"每次操作后重取子树"，服务端渲染反而更简单、更正确。

代价也很实在：页面切换有白屏、交互需要手写 DOM 操作、没有类型检查。我用两条经验规则兜底：任何超过 300 行的页面拆成独立 HTML；所有接口调用收敛在一个 `api.js` 里。这两条规则让我一年下来没有陷入过前端泥潭。

## 5 内部通信平面

### 5.1 协议：4 字节大端长度 + JSON

内部 RPC 协议叫 pymsg，格式简单到可以用一句话说清：`[4 字节大端无符号长度][UTF-8 JSON 载荷]`。服务端按 `_route` 字段分发，响应是同样的帧。

选它而不是 gRPC/HTTP 的理由，按重要性排序：

1. **跨语言成本**。系统里有 C++、Python、Go、仓颉（Cangjie）四种语言。长度前缀加 JSON 在四种语言里的实现都不超过 200 行，而 gRPC 需要为每种语言维护 protobuf 工具链。
2. **调试友好**。任何一个 socket 抓包工具都能直接看到可读的 JSON，不需要 .proto 文件和解码器。
3. **没有框架**。不需要 HTTP/2、不需要流控、不需要 header 语义。服务之间只有请求-响应，没有流式需求。

它不是没有缺点：没有模式校验（schema），字段写错只会在运行时暴露；没有多路复用，一个连接同时只能有一个在途请求；大对象（比如几 MB 的文件）不适合走这条路，所以文件走 HTTP Range 而不是 pymsg。这些都是清醒接受的限制。

### 5.2 演进策略：接口兼容的重写

项目里有一组"同名不同语言"的服务：Python 的 `db`/`dnfs`/`static`/`captcha`/`confs`，和 C++20 的 `db2`/`dnfs2`/`fsys`/`captcha2`。后者是前者的重写，要求是**协议、路由、错误语义、甚至 `$now` 这种哨兵值都完全一致**，做到调用方零改动切换。

这个策略的实际收益比想象中大：

- 切换是**可回退**的。改 `services.yaml` 里一行 `cmd` 就能换回 Python 版，因此重写过程可以分批验证，而不是一次性赌博。
- 重写过程逼迫我把"隐含契约"显式化。比如 Python 版的错误响应里会带 IP 和用户名，C++ 版在重写时统一脱敏——**契约一致，实现更严**，这是重写最有价值的产出。
- 性能与常驻内存顺带改善（第 9 节），但这从来不是主因。

代价是仓库里长期存在两份实现。我用"遗留"标签在 README 里明确标注，并在 `services.yaml` 里只保留新版的启动项。**代码仓库允许冗余，运行配置不允许模糊**——这是我给自己定的规矩。

### 5.3 数据访问收敛：db2

所有业务服务都不直连数据库，而是通过 pymsg 向 `db2:8005` 发结构化查询：`{action, table, where, values}`，由 db2 翻译成参数化 SQL。

三层防护是显式的：

- **表名白名单**（字母数字下划线）；
- **`sqlite3_bind_text` 参数绑定**，杜绝拼接注入；
- **只反射已有表**，协议层面无法执行 DDL（想建表得跑迁移脚本）。

并发模型是 per-thread 连接：每个 worker 线程持有独立 `sqlite3*`（`thread_local`），列 schema 加锁缓存，PRAGMA 与 Python 版对齐（WAL / NORMAL / busy_timeout=5000）。这样既避免了连接池，也避免了跨线程使用 handle 的经典崩溃。

这个设计的边界也必须说清：**它是"把数据库变成服务"，不是"把数据库变成分布式数据库"**。没有分片、没有读写分离、没有跨库事务。数据库文件 11 MB，SQLite 是唯一后端。如果哪天数据量涨到需要 Postgres，我会换掉 db2 的实现，但**协议不变**——这又是接口兼容策略的一次复用。

### 5.4 顺带一提：memdb

`memdb:8011` 是一个用模板库实现的 TTL 内存缓存，三索引（list 主存 + hashmap 键索引 + multiset TTL 索引），9 条路由。它目前**没有任何业务调用方**，属于"预留"。我在论文里写它，是因为它代表一种常见的诱惑：为未来可能的需求提前造轮子。我的自我约束是——预留可以，但必须**已接线、可观测、有测试**，否则三个月后没人知道它是干什么的。它现在挂在 `services.yaml` 里随系统启动，占 4.7 MB，这就是它的全部成本。

## 6 安全分层的工程化

### 6.1 三道闸门，职责不能混

系统的安全边界由三个进程串成：`waf`（边缘）、`ca`（认证）、`gateway`（转发）。这个拆法不是教科书式的"纵深防御"口号，它来自一次重构。

早期版本里，`gateway` 同时做验签和转发，`ca` 不存在。问题出现在两处：一是验签逻辑要跟着业务调整（比如某接口需要管理员权限），改一次就要重启入口；二是 `gateway` 既验签又转发，等于把"谁能进来"和"进来能去哪"耦合成一个组件，任何一侧出问题都会互相污染。

v0.9.0 的重构把认证整体搬到 `ca`，`gateway` 退化为纯转发并强制 loopback 自检。这个拆分带来的直接好处是**每条规则只有一个归属**：

- 攻击特征匹配 → waf（可热加载，`SIGHUP` 生效，不影响业务）
- 身份与令牌 → ca（RSA 密钥内存生成，重启即全失效）
- 路由白名单 → gateway（配置热更新，来自 core 内嵌 confs）

### 6.2 认证实现里的几个决定

- **密码**：PBKDF2-HMAC-SHA256，10 万轮，16 字节随机盐，常数时间比较。没有用 Argon2，因为要跨语言实现（C++ 侧只有 OpenSSL），而 PBKDF2 在 OpenSSL 里是一等公民。
- **令牌**：`Base64(payload) + "_" + RSA-Sign(payload)`，默认 1 小时。RSA 密钥对**启动时内存生成**——这意味着重启后所有旧 Token 失效。这不是缺陷，是特性：一个个人系统重启频率极低，而"重启即吊销全部会话"在应急时是最好用的开关。
- **Cookie 回退**：浏览器场景下同时签发 `HttpOnly + Secure + SameSite=Lax` 的 Cookie；验签时若无 `Authorization` 头则读 Cookie，并向下游补一个 `Authorization: Bearer`——**下游零改动**。这个"补头"策略让我在不改任何业务服务的前提下拿到了 HttpOnly 的安全收益。
- **双轨吊销**：jti 黑名单（精确）+ 用户版本号（批量）。前者用于单点登出，后者用于"改密码即踢掉所有设备"。
- **限流与验证码**：登录 5 次/5 分钟、注册 3 次/10 分钟；登录强制图形验证码（`captcha2`，一次性 Token、5 分钟过期、XOR 比较防时序）；注册需邮箱验证码（`smtp`，10 分钟有效、60 秒冷却、失败 5 次作废）。

### 6.3 fail-closed：一个反直觉但正确的默认

内容审核 `ai_review` 用 DeepSeek + ChromaDB 做 RAG：先把待审文本向量化，检索 top-3 相似的历史标注样本，注入 prompt，再让模型判定是否违规（色情、赌博、诈骗、仇恨暴力等）。

关键决策是**失败即拦截**：API 超时、响应解析失败、知识库不可用，一律返回 `{"invalid": "true"}`。对一个日均写入量很小的笔记系统，误拦一条内容的代价是用户再点一次，漏放一条的代价是站点被举报。这个不对称决定了默认值。

同理，`dnfs2` 的 Token 验签失败返回 503 而不是放行——**认证服务的不可用不应该被解释为"无需认证"**。这条原则听起来是常识，但我在早期版本里确实写错过（Python 版在 ca 不可达时降级放行），这也是它被重写的直接原因之一。

### 6.4 几个踩过的坑

- **身份头 strip-then-set**：客户端可以自己发 `X-Auth-User`。所以 `ca` 必须先剥掉客户端传来的所有身份头，再写入自己的判定值。这个顺序写反过一次，等于任意用户可伪造管理员。
- **`Proxy.opened` 白名单必须显式**：早期"缺省放行"意味着新增内部服务会自动对外暴露。现在缺省走 `Proxy.default`（一个明确的拒绝或兜底目标），暴露需要主动加白。
- **上游不可达统一 502**：不要暴露 "connection refused to 127.0.0.1:8007" 这种信息，那等于免费给攻击者一张内网拓扑图。

## 7 可观测性：把日志当数据

### 7.1 Logs 表

我没有部署 ELK，也没有上 Prometheus。日志的去处是 `db2` 里的一张 `Logs` 表（`service / level / message / trace_id / extra` + 4 个索引），各服务通过一份 150 行的 `log_client` SDK 异步写入：内存队列 + 后台线程，每 2 秒或攒够 50 条批量 flush，**db2 不可用时静默丢弃**（fail-safe，绝不让日志拖垮业务）。

后台线程每小时清理一次：保留 30 天，上限 100 万条。于是"日志保留策略"这个通常要配一整套生命周期的需求，变成了两行常量。

查询就是 SQL：

```sql
SELECT service, level, count(*) FROM Logs
WHERE ts > datetime('now','-1 hour') GROUP BY 1,2;
```

对我来说这比 PromQL 直观得多，代价是没有聚合预计算、没有告警规则引擎、没有可视化面板。第 10 节会说明这个代价在什么规模下会变得不可接受。

### 7.2 副产物：统一日志让故障排查变快

因为所有服务的日志落在同一张表、带同一个 `trace_id` 字段，排查一个跨服务问题时不需要登录多台机器 `grep`。今天这次开机链路的排查（第 8 节）就是靠 `journalctl` 加 `Logs` 表交叉验证完成的：systemd 侧看到"job timed out"，业务侧看到"ca 启动晚于预期"，两边一对，因果立现。

## 8 部署与运维：真实世界的 90 秒

### 8.1 部署形态

`systemd` 只认一个单元：`nidus.service`，启动 `core`，`core` 拉起 11 个子进程。安装脚本按依赖顺序编译（库先行，core 最后），部署路径约定为 `/opt/micro_servers/`。

没有容器。这不是对容器的否定，而是在"单机 + 单一负责人"的场景下，容器带来的隔离收益抵不过镜像构建、网络命名空间、卷挂载的维护成本。**一旦服务需要跨机器，这个结论立刻反转**。

### 8.2 一次开机链路的解剖

今天的实测值：内核把控制权交给 userspace 后 **8.35 秒**到达 `graphical.target`，开机后 **17 秒**（12:39:44 → 12:40:01）全部 11 个服务端口就绪。但这个 8 秒是修完之后的结果，修之前是 **1 分 34 秒**。

诊断过程值得记录，因为它精确地展示了"声明式依赖"的陷阱。开机日志里有一条：

```
12:01:32 Job sys-subsystem-net-devices-wlx200db0c2434f.device/start timed out.
12:01:32 Dependency failed for netplan-wpa-wlx200db0c2434f.service
```

因果链是这样的：一块 USB 无线网卡被拔掉了，但 netplan 仍然为它生成了 `netplan-wpa` 服务，该服务带有 `Requires=<device>` 和 `Before=network.target`。设备不存在 → device job 等满 90 秒超时 → `network.target` 被它阻塞 → 依赖 `network.target` 的 docker、frpc、业务服务全部顺延 → 连 docker 的 netns 挂载单元都被拖到 1 分 34 秒（它看起来像"另一个在等的问题"，其实是同一个）。

修法有三层，最后选了最朴素的一层：

1. 给网卡加 `optional: true` —— **无效**，netplan 不会因此改变 unit 的 ordering；
2. 给 device 单元加 `JobTimeoutSec=8s` 的 drop-in —— **有效**，实测 8.02 秒放弃等待；
3. 确认这块网卡确实不再使用后，直接停用无线网卡配置 —— **更彻底**，相关单元从 `/run` 里彻底消失。

同样的逻辑还解释了另一个现象：控制台面板"花屏"。这台机器有一个跑在 tty1 上用 fbterm 渲染的监控面板，而内核与 systemd 的启动消息也写在 tty1，两者抢同一块 framebuffer。修法是把控制台整体迁走：

```
GRUB_CMDLINE_LINUX_DEFAULT="pci=realloc quiet loglevel=3 console=tty3"
```

`console=tty3` 让启动日志全部落到第三号虚拟终端（`Alt+F3` 可查看），tty1 完整让给面板。一行配置，一个长期存在的"界面被刷掉"问题消失。

### 8.3 教训

这两件事的共同点是：**系统的默认行为在"资源存在"的前提下是正确的**，一旦某个资源缺席，依赖它的声明式约束就会变成最长的那根木板。所以我现在维护 `services.yaml` 和 netplan 时遵守一条规则：

> 区分"必须"与"最好有"。必须的写成 `Requires=`，最好有的写成 `Wants=` 并显式给出超时。

顺带一提，`redirect80`（80→443 重定向）目前是停用状态，因为 80 端口被机器上的另一个系统服务占用。这就是"单机多系统"的真实形态：端口不是无限的，冲突靠人工裁决，配置文件里的注释就是裁决记录。

## 9 评测

测量条件：单台 x86_64 主机（16 GB 内存），所有服务运行在同一台机器的回环/本机网卡上，因此下文延迟**不含任何外部网络 RTT**。数据取自 2026-11-14 的稳定运行态。

### 9.1 资源占用

| 进程 | 语言 | RSS (MB) |
|---|---|---|
| ca | C++20 | 18.8 |
| waf | Go | 16.4 |
| gateway | C++20 | 14.9 |
| fsys | C++20 | 14.8 |
| core (nidus) | C++20 | 13.2 |
| dnfs2 | C++20 | 13.0 |
| db2 | C++20 | 7.6 |
| captcha2 | C++20 | 7.2 |
| memdb | C++20 | 4.7 |

主链路 9 个进程合计 **约 111 MB**。Python 侧：`smtp` 约 17 MB，`ai_review` 约 123 MB（主要来自 ChromaDB 与推理运行时），`aibox` 约 23 MB。整机常驻内存 3.4 GB（含 PyTorch、Ollama 式推理服务等无关进程），系统留有 12 GB 可用。

一个 C++ 微服务常驻 7~19 MB，而同等功能的 Python/Flask 服务通常在 60~100 MB。**这是我选择重写的第一个真实动机**：在一台要和 GPU 推理抢内存的机器上，10 个服务的内存差异是 GB 级的。

### 9.2 延迟

端到端（客户端 → waf → ca → gateway → fsys → 返回）：

| 路径 | HTTP | 首字节 | 总耗时 | 响应体 |
|---|---|---|---|---|
| `GET /`（首页，五跳） | 200 | 12.7 ms | 12.8 ms | 14.3 KB |
| `GET /captcha/image`（含 PNG 生成 + 代理） | 200 | 14.2 ms | 14.3 ms | 2.2 KB |

其中 TLS 握手占 7.6~8.0 ms，即**安全链路本身的成本大于业务成本**。这个比例在小文件上是常态，也说明多一跳转发的边际成本很低（约 1~2 ms）。它同时提醒我：五跳结构的合理性完全建立在"本机回环"之上。

### 9.3 启动

| 阶段 | 修复前 | 修复后 |
|---|---|---|
| kernel → graphical.target（userspace） | 1 min 34.6 s | 8.35 s |
| 开机 → 全部服务端口就绪 | ≈ 1 min 50 s | 17 s |

11 个进程的拉起是同批完成的（同一秒内全部监听），说明 `core` 的顺序启动开销可以忽略。

### 9.4 代码规模

自研代码约 **71,400 行**（排除虚拟环境、第三方库与构建产物）：

- 主链路 C++ 服务（core / ca / gateway / fsys / dnfs2 / db2 / memdb / captcha2）约 **14,500 行**；
- 共享库（libhttp / libmsg / libcrypt / libth / libsqlite3 / liblogc / libtry）约 **7,100 行**；
- 协议与 Python 侧（pymsg / smtp / ai_review / redirect80）约 **2,900 行**；
- AI 智能体子系统 aibox 约 27,400 行（独立产品，不计入主干）。

这个规模的意义在于：**整个系统的核心可以在两周内被一个人重新读懂**。可读性是我最看重的非功能需求，因为唯一的维护者就是我自己，而我会忘。

## 10 讨论：适用边界

我不认为这套架构具有普适性。它成立依赖四个前提，缺一个就该换方案。

**(1) 单一运维主体。** 服务的启动顺序、端口分配、配置注入都是人工维护的常量。人数超过 3~5 人，这些"脑内约定"就会开始失效，此时应该上配置中心与服务发现。

**(2) 单机部署。** 所有服务共享回环网络，五跳转发的成本才可以忽略。一旦跨机器，`gateway` 的白名单、`ca` 的转发、`db2` 的 loopback 绑定全部需要重做——那时应该考虑 K8s 或至少 Nomad。

**(3) 数据规模在单机 SQLite 的舒适区内。** 当前数据库 11 MB，日志表上限 100 万条。数据量再上两个数量级，`db2` 的 per-thread 连接模型与单写者模型会成为瓶颈，该换 Postgres 并保留协议。

**(4) 团队能读写 C++。** 这是最硬的门槛。这套系统的性能与内存收益，是用"内存安全和并发正确性要自己保证"换来的。如果团队主力是 Python/TS，同样架构用 Go 实现会务实得多——pymsg 在 Go 里大概 150 行。

反过来，我还想点名几个我认为**明确错误**的用法：

- 用这套东西做多租户 SaaS：没有资源隔离，一个租户的慢查询会拖垮全部；
- 把 `ai_review` 这种外部 API 依赖放在主写入链路上而不设超时与降级：一次 DeepSeek 抖动就等于全站无法写笔记（当前用 fail-closed + 10 s 超时兜底，但这是"可接受地失败"，不是"高可用"）；
- 在 `services.yaml` 里堆砌 `depends_on` 却不用它做拓扑排序：它现在只是注释，别指望它救命（第 8 节已经证明了这一点）。

## 11 局限与未来工作

诚实列出我知道的问题：

1. **`depends_on` 名不副实**。当前只记录顺序，不做求解。要么实现 DAG 拓扑排序 + 就绪探针，要么改名为 `start_order`，别让它误导人。
2. **`services.yaml` 单点**。它是启动的唯一真相源，却没有 schema 校验。一个缩进错误会让整个系统起不来，而错误信息来自 YAML 解析器。
3. **没有自动化性能回归**。第 9 节的数字是手工测的。理想状态是每次构建跑一遍回环基准，把延迟和 RSS 写进 `Logs` 表，用 SQL 看趋势。
4. **`smtp` 仍是 Python**（C++ 重写版待切换），且验证码存进程内存，不支持多实例——在单机前提下这没问题，但它是"接口兼容重写"策略里唯一没走完的一条线。
5. **`memdb` 无调用方**。要么接一个真实场景（会话缓存最合适），要么下线。预留超过半年就该怀疑自己。

未来工作的优先级我认为是：**先给 `services.yaml` 加 schema 校验**（成本最低、收益最直接），再做启动依赖的显式化，最后才是性能基准。至于"要不要上容器"，我的答案仍然是不要——直到它需要跨机器。

---

## 12 结论

这套系统没有发明任何新技术。它做的事情是把一组众所周知的技术（TLS 终止、WAF 规则、令牌认证、长度前缀 RPC、SQLite、进程守护）按一个明确的价值排序重新组合：**先保证能被一个人理解，再保证能被一个人维护，最后才追求性能与扩展性**。

它的量化结果是：11 个进程、110 MB 内存、17 秒冷启动、12.8 ms 端到端延迟、7 万行自研代码、一台机器。

它的定性结果是：改一行 CSS 不需要构建，加一个内部服务不需要写编排文件，查一个跨服务问题不需要登录三台机器，而一次开机慢 90 秒的原因可以被精确定位到一块不存在的网卡上。

如果这篇文章有什么可迁移的结论，大概是两条：

- **微服务的价值在边界，不在容器。** 把边界划在数据和信任上，部署形态可以非常朴素。
- **默认值是有前提的。** 无论是 netplan 的 `Requires=`、systemd 的 90 秒 job 超时，还是"前端就该分离"这条行业共识——它们都在某个前提下才成立。工程判断的本质，是知道自己站在哪个前提上。
